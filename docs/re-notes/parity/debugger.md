## Debug events

The kernel calls the debug routine (`KiDebugRoutine`, located through debug monitor data +0x00) from `KiDispatchException2` on the faulting thread: `r3` trap frame, `r4` exception record, `r5` context (flags 0x17), `r6` 0 first chance / 1 second chance; nonzero return means handled and the context is restored. Thread creation and termination arrive through `ExRegisterThreadNotification` (routine at registration +0, called as `(registration, thread, create)` on the thread concerned). Stock processes both on the calling thread (0x91f3a980 -> 0x91f39fc0, 0x91f32530 -> 0x91f39b30).

The reimplementation splits this. Thread creation and termination are posted without waiting, as stock queues them, except a creation that may stop (`stopon createthread`, or a title entry thread). Every other event is posted to a slot while the calling thread waits on a synchronization event, but only while the server thread runs its pass loop; before the first pass and after the loop ends, the thread takes the in-place dispatch of a thread that cannot wait (below) or the event's default disposition, and a waiting thread is released at its next 100 ms check. While posted, the server thread takes it (`Backend::next_event`), runs the port of 0x91f39fc0 (`events.rs`), and completes it with a disposition (handled, write dump, chain to the previous routine, break after a thread start). A stopping event stays pending until `continue`, a state change that releases stopped threads (go from pending_title, request reboot_title, `kd except`, break-in), and what stock does after its wait (step over a breakpoint, assertion "ignore" answer, step past a trap) runs then.

Stock does all of an event's work on the faulting thread. 0x91f3a980 switches to a kernel stack of the thread's process type (0x8000 bytes each, MmCreateKernelStack in 0x91f3bc38) under that type's critical section (0x91fadcc0 for process type 2, 0x91fadca0 otherwise) and runs 0x91f39fc0, which for a stop calls 0x91f39d08: 0x91f25da0 resets the record event, sets record flag 0x8 and changes execution to stopped (0x91f2da88: thread suspension and the `execution stopped` line); 0x91f39ad0 formats the line (0x91f391e0) and, at passive level, 0x91f39688 sends it to every notification socket under critical section 0x91fadd00 (0x91f389e0: select for writability with a 60 s limit, then send); 0x91f25e20 then waits without a timeout on the record event, which `continue` sets (0x91f25d40). The command thread only releases the wait. Here the faulting thread posts and waits; the dispatch, the execution change, the suspension of other threads and the lines run on the server thread when its pass loop takes the slot.

Implemented dispatch, as in 0x91f39fc0: first-chance trap rewrite (0x91f39ef0); breakpoint (stops only a thread that can stop, 0x91f3a110: debuggable, Msr EE, attached in dump mode `enabled`, and, for an address not in the table, no kernel debugger routing; otherwise a table breakpoint is reported without a stop when the thread is debuggable, stepped over and handled, and any other breakpoint ends unresolved without a line, 0x91f3a22c..0x91f3a2f0; table breakpoints are lifted for a trace step and re-armed on the step exception; an embedded trap is stepped past); debug strings (stop on `debugstr`, string read from r3/r4); module load (stop on `modload`, description from the loader entry and image header, `modload` line format of 0x91f39080); module unload (breakpoints in the range removed); assertion prompts (`assert ... stop stop`, r3 set to 0x49 and Iar advanced when unchanged); rip; ntassert (0xc0000420, only when it can stop); single step and the data breakpoint (data kinds 1 and 2 print `write`/`read`; kind 5 prints nothing because the formatter knows only 1..3); generic exceptions (stop when second chance or `fce`; `first`/`noncont` flags; access violation `read=`/`write=`; thread-name exception 0x406d1388 names the thread); unhandled end (`kd lite` chain or Iar += 4 and r3 = 0); crash dump on unhandled second-chance exceptions unless dump mode is disabled; auto-go when nobody receives a stop notification in dump mode `enabled`; a stop requested while execution is stopped or pending waits until the state changes; data breakpoint register reprogrammed after each event. Control code 0xa4 enables the first-chance breakpoint/trace pass-through.

## Control dispatcher

`docs/re-notes/dispatcher.md` documents every code. `backend/dispatcher.rs` publishes the dispatcher at data block +0x18 and `KeDebugMonitorData` (ordinal 89), passes every result through the extension `OnTellDebugger` hook, implements the debugger codes (0x01 break-in poll, 0x19, 0x34, 0x35, 0x63, 0xa4) and routes other domains' codes to their `service_*` functions. Requests that need server state (settings write, break-in, kd lite refresh) are queued and applied by the server thread (`dispatcher::drain`).

## Events that cannot wait (stock deferred queue 0x91f39768)

Exceptions above passive level, on the server thread, of a thread that overflowed its stack, and of a thread that already waits in its slot are dispatched in place by `dispatch_direct` (`debugger/direct.rs`) with the `DirectPolicy` the server publishes after every pass (`publish_direct_policy`), under the breakpoint table lock. Such a thread cannot stop. Up to dispatch level a notification is queued only when a debugger is attached and `eventdefer` selects its kind (break 1, debugstring 2, singlestep 4, assert 8, ntassert 0x10, databreak 0x20, rip 0x40); a queued assert or rip resolves as a continue (r3 = 0x49, Iar + 4), a queued data breakpoint steps over the register, and a queued single step steps over a table breakpoint at the new Iar (0x91f3a68c, 0x91f27550). A table breakpoint is reported without a stop when the record is debuggable (`DirectNotice::Break`), lifted for a trace step (0x91f27550) and handled; the step's trace exception re-arms it (0x91f27630). Any other breakpoint ends unresolved. A nested exception of a thread waiting in its slot (stock record +0xc set, 0x91f3a0e4) restores the instruction of a table breakpoint at Iar and resumes (0x91f3a1b0, 0x91f26b80), else ends unresolved. On the server thread every line is sent. The platform captures text and module descriptions into pool nodes (tag `Ddfn`, pool type 2) and the server delivers them (`next_direct_notification`). A module unload removes the module's breakpoints during the dispatch (0x91f3a3dc), even when no line is sent.

The in-place step state (the step over a breakpoint or the data breakpoint, stock's deferred dispatch context at 0x91fae9b0) and the breakpoint table are `BreakpointState`, which the platform keeps under its table lock (`Backend::lock_breakpoints`): on the console a kernel spin lock taken at IRQL 0x7c, as stock spin lock 0x91fae9c0 (`backend/debugger/table.rs`); on the host the host lock. The server takes the lock around every table access. A set (`Backend::set_breakpoint`) obtains the spare block from pool memory before taking the lock, as stock allocates before raising IRQL (0x91f27000..0x91f27028); on the console sets are serialized by a critical section (stock 0x91fae960) and blocks are 0x488 bytes of system pool with tag `Xbdm`.

## Events during a dispatch flag 0x4 command

While the server thread waits for the thread of a dispatch flag 0x4 command (`civinject`, `civstart`, `civstop`, `civverify`; `dispatcher::block_posts` around `run_command_thread`), only events that stop their thread wait for it. A passive-level exception is first tested on the raising thread with the stop rules of 0x91f39fc0 (`exception_stops` in `direct.rs`: trap pass-through, dump written, can stop, the trap kind, `stopon`, the table for a breakpoint under kernel debugger routing, the data breakpoint overlap, and a pending step over that ends without a stop, which the server publishes per process as `DirectPolicy::quiet_step`); a stack overflow of a thread that can stop always stops. Such an event claims a slot and waits as at any other time, and its slot is not reclaimed while the command runs: the server takes it after the command returns, so the thread stays stopped as stock's would (a command thread that stops waits the same way). Any other event is dispatched in place with `Delivery::Inline` (every notification is queued for the server, as stock's raising thread sends it itself) and takes the disposition the monitor gives it without a stop, so that a thread the command waits for (XAM's worker printing a debug string) never waits for the server. Thread creation is posted without waiting even when it could stop; a detached post that finds no free slot is dropped. Execution requests from other threads (`request_execution`, `stop_at_pending_title`, `report_pogo_module_start`) do nothing, as before the first pass. `call_on_server` requests fail (none is taken; a posted request is withdrawn at the poster's next 100 ms check). Deviation: the notifications of that window reach the channels after the command's reply instead of during the command, a stop's `execution stopped` and stop lines follow the reply, a thread creation stop (`stopon createthread`) does not stop, and execution changes requested in it are lost. The stop test reads the policy the server published at the end of its previous pass, so a `stopon` or `debugger` change made by an earlier command of the same pass is not yet seen. Stock's server thread is blocked the same way, but its posters never wait for it.

## `break now`

The command thread executes the trap (stock 0x91f48a6c) and the debug routine dispatches it in place, as for any exception of the server thread. The command thread's record is not debuggable (stock 0x91f50cf0 clears 0x2000; openxbdm's server thread record likewise), so it cannot stop: the trap ends unresolved, with a crash dump unless dump mode is disabled or the kernel debugger flag is set, then the `kd lite` chain, else r3 = 0 and Iar + 4. `break now` then replies `200- OK` without testing the other keys (0x91f48a74). With the default settings this writes a crash dump and restarts the console, as stock does.

## Execution requests from other threads

`request_execution(target, notify)` (stock 0x91f2da88 with the wait flag clear), `stop_at_pending_title(forever)` (`execution pending_title stop`; after the 15 s timeout the wait ends unreleased and the launching thread prints its trace and starts execution itself, as stock 0x91f523a0), and `report_pogo_module_start(name, module)` (stopon pogomodstart) post `DebugEvent::ExecutionRequest`, `PendingTitleStop`, and `PogoModuleStart` through the event slots. `threads_block_relaunch` ports 0x91f276d8 over the stopped-event table.

## Stack overflow

`install` stores the naked entry `stack_overflow_entry` (stock 0x91f23330, installed by 0x91f3bc38 right after the debug routine hook) through `KiStackOverflowNotification` (data block +0x58). Stock stores through the word without a check (0x91f3bdec); the query service always fills it (K16547 0x800894d4, K15574 0x8008935c, `KiStackOverflowNotification` 0x801fb914), so `install` stores unconditionally too. The kernel calls it with interrupts off and `r3` = trap frame just before `KeBugCheckEx(0x2b, ...)`; the entry stores r13..r31 into the frame register area (GPR n at +0x50 + 8n, so r13 at +0xb8) and runs `stack_overflow` (stock 0x91f3aab0) behind the export bridge. That routine exchanges the notification pointer with 0 (one shot); returns at once when it was already 0 or the kernel debugger is enabled and attached (hardware flag 0x100); can stop when the thread's monitor record is debuggable, IRQL is passive, the trap frame Msr low word (+0x1b4) is nonzero and not (dump mode enabled without an attached debugger). Otherwise it returns unless the dump mode allows a dump. It then marks the thread's monitor record (flag 0x40, `MonitorRecordFlags::STACK_OVERFLOW`, stock 0x91f3abb0); every later exception of that thread is dispatched in place and ends unresolved (stock 0x91f3a0d8 after the pass-through and dump-written tests: crash dump unless dump mode is disabled, a dump was written or the kernel debugger flag is set, then the `kd lite` chain or r3 = 0 and Iar + 4), including one raised while the thread waits in its slot. It builds the context with `KeContextFromKframes(frame, context)` (flags 0x17) and a 0x50-byte record (code 0xc00000fd, flags 1, address = frame +0x1ac). A thread that can stop sets the interrupt enable bit and posts `KIND_STACK_OVERFLOW` (`DebugEvent::StackOverflow`, `can_stop` true) until the disposition is no longer `handled`; `getcontext`/`setcontext` use the built context while it waits. The dump (data block +0x0c bit 0x40, `DumpWriteDump(record, context, 0)`) follows when the last disposition asks for it, or directly when the thread cannot stop. The routine returns the faulting address. The kd, dump-mode and attached tests made before posting read the policy the server published at its last pass; the server repeats them on its own state.

## Software breakpoint table

`breakpoints.rs` keeps stock's block chain (head 0x91fae980, spare 0x91fae97c). A block holds a count, 0x80 sorted addresses, the saved instruction words, flag bytes (bit 0 trap written; arming also skips bit 1, which has no writer) and the next link (stock 0x488 bytes, pool tag `Xbdm`, type 2). Every block comes from pool memory through the backend's scratch allocation and is never freed, so a set fails only when a block it needs (the first one, or the spare for a split) cannot be allocated. The lookup (0x91f25480) picks the block whose first address is at or below the address and whose successor's first address is above it, else the last block, then binary-searches it; a miss in a full block splits it with the spare (upper half moves) and continues in the half that covers the address. Set (0x91f26fc8) rejects unaligned addresses, allocates a spare when none is held, inserts with the saved word at the new index left as it was, and reports success even when the trap cannot be written. Remove (0x91f27178), clear all (0x91f27290: counts set to 0, blocks kept), module unload (0x91f26e90) and the getmemex restore (0x91f256d0) follow stock, including the whole-walk stop at a block whose first address is at or past the range end. Stale first addresses of emptied blocks keep steering the lookup, and an entry set below the head's first address goes to the last block, which can leave entries of earlier blocks unreachable. A step over a breakpoint records the block's address and the index (0x91f27550) and re-arms whatever entry is there afterwards (0x91f27630).

## Exports

`crates/openxbdm-server-xbox360/src/backend/debugger/exports.rs` implements the debugger domain's exports with the same code as the commands: 8 (`continue`), 13/41 (`getcontext`/`setcontext` context reads and writes, by kernel context layout in caller memory), 15 (`threads` list; stops visiting at capacity, 0x82da0105), 19 (`go`), 21/373 (`debugger` flag, address word, port, from mirrors the server publishes each pass), 22 (`isstopped` stop record, `StopReason::encode`), 34/37 (`break addr=` clear/set, on the calling thread under the table lock with the spare allocated before it, stock 0x91f27258, 0x91f27140), 35/48 (`resume`/`suspend`), 38 (data breakpoint by type 0/1/2/5), 39 (`break start`), 45 (`stop`), 46 (`stopon`/`nostopon` mask), 49 (record debug data word of the calling thread), 56 (`isbreak`), 82 (stack back trace from the caller's frame, `RtlGetStackLimits` krnl 0x12a, stock IAT 0x91f006b0), 83 (dump of the calling thread), 89 (size-versioned `threadinfo` record), 178/179 (`dbgextld` load and release), 180 (`ExCreateThread` with flags 0x4000026, suspended for caller flag 4). Exports needing server state go through `dispatcher::call_on_server` and return E_UNEXPECTED where it cannot run (server thread, above passive level, during a dispatch flag 0x4 command); export 46 queues its change instead.

## `getcontext`

The handler reads the context once (export 13 semantics) into a 0xa50-byte pool block (`400- out of memory` when the allocation fails, as stock 0x91f482b0) and the lines come from that copy; the block is freed by the last continuation call, or at the next event pass when the connection closed first.

## Remaining gaps (precise)

- Event latency: stock does an event's dispatch, execution change, thread suspension and notification sends on the faulting thread (see debug events); here the server thread does them. A posting thread sends one byte to the server's wake socket (`backend/debugger/wake.rs`), which the server includes in its select, so the pass that takes the event starts at once instead of up to 20 ms later. At server start the socket's target is chosen by sending a test datagram to 127.0.0.1, then to the debug address, waiting 100 ms for each; when neither arrives the socket is closed and events wait for the next pass (at most 20 ms, the pass interval that other queues of the server thread keep in any case). What remains: the work still runs on the server thread, after whatever that thread is doing (a command in progress, a blocking send), and the direct path and the stack overflow tests read the policy published at the last pass. Whether XNet delivers the self-addressed datagram is not established from the image; the wake-probe module checks it on hardware.
- Stopped-thread release by a state change applies only to debuggable threads, as stock's 0x91f2da88 does; a non-debuggable launcher thread in `stop_at_pending_title` therefore waits for its timeout.

## Deviations

Stock defects openxbdm does not reproduce:

- `isstopped` of a data breakpoint stop (type 0xd): export 22 writes only the type, Iar and thread for it (0x91f2618c..0x91f261b0), `isstopped` passes an uninitialized stack buffer (0x91f48dd0), and the formatter takes the access kind from the unwritten word +0xc (0x91f392c8), an uninitialized read. Here the kind is outside 1..3, so the reply is `stopped`.
- Breakpoint block split: stock leaves the upper block's unused slots as the pool returned them (0x91f255c4..0x91f25654; only a new head is cleared, 0x91f25510). Here every block is zeroed when obtained.
- Stack overflow of a thread without a monitor record: stock stores flag 0x40 through the null record pointer (0x91f3ab9c, address 0x10) whenever the dump mode allows a dump. Here nothing is marked.

## Nuances

- `assert` notifications that stop end in ` stop stop` (the assert formatter appends the suffix and falls into the common suffix code).
- `halt` always fails with `400- ` on dev kits.
- `debugger` settings line prints the address low byte first; a peer address taken from the connection is therefore written reversed.
- Re-setting an identical data breakpoint clears the hardware register until the next debug exception.
- isstopped of an ntassert stop reports `exception code=0xc0000420`, because the builder tests code 0x15.
- `continue exception` has no effect on breakpoints, single steps, asserts and rips; it only marks generic first-chance exceptions unhandled.
- Record flag 0x100 (tested by 0x91f276d8 for trap 0x16 stops) is never set, so that test always passes on to the breakpoint table lookup. Every store to record +0x10 in the image sets only 0x2, 0x4, 0x8, 0x20, 0x40, 0x80, 0x200, 0x1000, 0x2000, 0x01000000 or 0x02000000 (0x91f310a0, 0x91f310b8, 0x91f25d24, 0x91f25dfc, 0x91f2df48, 0x91f324c0, 0x91f324dc, 0x91f32594, 0x91f3a284, 0x91f3a6fc, 0x91f3a7e0, 0x91f3aa38, 0x91f3abb0, 0x91f42b34, 0x91f50bc8, 0x91f50cdc, 0x91f5250c, 0x91f61720, 0x91f6174c), clears bits (0x91f25d3c, 0x91f2dd70, 0x91f39bd4, 0x91f39be4, 0x91f39d88, 0x91f3a100, 0x91f3a2bc, 0x91f3a62c, 0x91f3a67c, 0x91f3a740, 0x91f3a88c, 0x91f3a8ec, 0x91f3aa7c, 0x91f3ac54, 0x91f50cf4, 0x91f5ff80, 0x91f60000, 0x91f61770), or restores bits 0x02003000 saved earlier (0x91f5ffb4, 0x91f60018). 0x91f39be4, after the title entry break trap of 0x91f39b30, is the only store that touches 0x100, and it clears it. Records are created by 0x91f31028 and reached only through thread +0x15c, whose loads in the image are all covered, and neither K16547 nor K15574 reads thread +0x15c.
